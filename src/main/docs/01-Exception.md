# 서블릿 예외 처리와 오류 화면

## 1. 처리되지 않은 예외는 어디까지 전달되는가

컨트롤러나 서비스에서 발생한 예외를 애플리케이션 내부에서 처리하지 못하면, 예외는 호출 경로를 거슬러 올라가 최종적으로 WAS까지 전달된다.

```text
Controller에서 예외 발생
← Interceptor
← DispatcherServlet
← Filter
← WAS
```

WAS는 이 요청을 정상적으로 처리할 수 없다고 판단하고 일반적으로 500 상태 코드를 반환한다.

반면 요청한 URL 자체를 처리할 대상이 없다면 404 상태 코드가 반환된다.

```text
404 → 요청한 대상을 찾지 못함
500 → 서버가 요청을 처리하던 중 오류 발생
```

---

## 2. `sendError()`로 오류 상태 전달하기

예외를 던지지 않고도 `HttpServletResponse`의 `sendError()`를 사용해 오류 상태를 전달할 수 있다.

```java
response.sendError(404);
```

`sendError()`는 새로운 예외를 발생시키는 코드가 아니다. 응답 객체에 오류 상태를 기록하고, 요청 처리가 WAS로 돌아갔을 때 WAS가 그 상태를 확인해 오류 응답을 만든다.

```text
컨트롤러에서 sendError() 호출
→ response에 오류 상태 기록
→ WAS가 상태 확인
→ 해당 상태 코드로 오류 응답 처리
```

즉, 처리되지 않은 예외와 `sendError()`는 시작 방식은 다르지만 최종 오류 응답은 WAS가 처리한다는 공통점이 있다.

---

## 3. 오류 종류와 처리 경로 연결하기

기본 오류 화면 대신 별도의 화면을 보여주려면 오류 종류와 처리 URL을 연결해야 한다.

```java
new ErrorPage(HttpStatus.NOT_FOUND, "/error-page/404");
new ErrorPage(HttpStatus.INTERNAL_SERVER_ERROR, "/error-page/500");
new ErrorPage(RuntimeException.class, "/error-page/500");
```

위 설정은 다음 의미를 가진다.

```text
404 상태 코드      → /error-page/404
500 상태 코드      → /error-page/500
RuntimeException   → /error-page/500
```

예외 타입으로 등록하면 해당 예외뿐 아니라 그 하위 타입도 같은 경로에서 처리된다.

---

## 4. `ErrorPage`의 URL은 화면 파일 경로가 아니다

`ErrorPage`에 작성한 URL은 HTML 파일 위치가 아니라, 오류가 발생했을 때 WAS가 다시 전달할 요청 경로다.

```text
오류 발생
→ WAS가 등록된 오류 경로로 다시 전달
→ 해당 URL의 컨트롤러 실행
→ 컨트롤러가 오류 뷰 이름 반환
→ 화면 렌더링
```

예를 들어 404 오류를 `/error-page/404`에 연결했다면, 해당 URL을 처리하는 컨트롤러가 필요하다.

```java
@RequestMapping("/error-page/404")
public String errorPage404() {
    return "error-page/404";
}
```

두 값은 역할이 다르다.

```text
/error-page/404 → WAS가 다시 요청하는 URL
error-page/404  → 컨트롤러가 반환하는 뷰 이름
```

따라서 `ErrorPage`는 오류 화면 파일을 직접 지정하는 설정이 아니라, 오류를 처리할 요청 경로를 연결하는 설정이다.

## 5. 오류 화면을 보여주기 위해 서버 내부에서 다시 요청한다

컨트롤러에서 처리되지 않은 예외가 발생하거나 `sendError()`가 호출되면 요청은 WAS로 돌아간다.

WAS는 등록된 `ErrorPage` 정보를 확인한 뒤, 해당 오류와 연결된 URL로 서버 내부 요청을 다시 보낸다.

```text
첫 번째 처리

클라이언트 요청
→ Filter
→ DispatcherServlet
→ Interceptor
→ Controller
→ 예외가 WAS까지 전달됨
```

```text
오류 화면 처리

WAS
→ 등록된 오류 처리 URL로 내부 전달
→ Filter
→ DispatcherServlet
→ Interceptor
→ 오류 처리 Controller
→ 오류 View
```

예를 들어 `RuntimeException`을 `/error-page/500`에 연결했다면, 예외가 WAS까지 전달된 뒤 `/error-page/500`을 처리하는 컨트롤러가 다시 실행된다.

이 과정은 브라우저가 오류 처리 URL을 새로 요청한 것이 아니다. 브라우저는 처음 보낸 요청에 대한 최종 응답만 받으며, 오류 화면을 찾는 과정은 서버 내부에서 진행된다.

---

## 6. 오류 처리 요청에는 발생한 오류 정보가 함께 전달된다

WAS는 오류 처리 URL만 다시 호출하는 것이 아니라, 처음 요청에서 발생한 오류 정보도 `request` 속성에 담아 전달한다.

오류 페이지에서는 필요에 따라 다음 정보를 확인할 수 있다.

```text
발생한 예외
예외 타입
오류 메시지
처음 요청한 URI
오류가 발생한 서블릿 이름
HTTP 상태 코드
```

서블릿에서는 이러한 값에 접근할 수 있도록 `RequestDispatcher`에 관련 상수를 제공한다.

```java
request.getAttribute(
        RequestDispatcher.ERROR_STATUS_CODE
);
```

모든 값을 화면에 노출해야 하는 것은 아니다. 이 정보는 오류 원인을 기록하거나, 상태 코드에 따라 화면을 구분하는 데 사용할 수 있다.

---

## 7. 오류 처리 URL에 직접 접근한 경우는 다르게 동작한다

브라우저에서 `/error-page/404` 같은 오류 처리 URL을 직접 입력할 수도 있다.

이 경우에는 실제 오류가 발생한 것이 아니라 일반 요청으로 해당 컨트롤러에 접근한 것이다. 따라서 WAS가 넣어 주는 예외 정보나 원래 요청 URI가 존재하지 않는다.

```text
실제 오류를 통해 이동

/error-ex 요청
→ 예외 발생
→ WAS가 /error-page/500으로 내부 전달
→ 오류 정보 존재
```

```text
오류 처리 URL에 직접 접근

/error-page/500 요청
→ 일반 컨트롤러 요청
→ 전달된 오류 정보 없음
```

같은 컨트롤러가 실행되더라도, 서버의 오류 처리 과정에서 호출됐는지 브라우저가 직접 호출했는지에 따라 요청에 담긴 정보가 달라진다.

---

## 8. `DispatcherType`으로 요청이 시작된 이유를 구분한다

오류 화면을 처리할 때는 서버 내부에서 요청 흐름이 한 번 더 실행된다. 그래서 필터와 DispatcherServlet도 다시 거칠 수 있다.

서블릿은 현재 요청이 어떤 이유로 전달됐는지 구분할 수 있도록 `DispatcherType`을 제공한다.

이번 범위에서 중요한 값은 다음 두 가지다.

```text
REQUEST
→ 브라우저에서 처음 들어온 일반 요청

ERROR
→ 오류 화면을 처리하기 위해 WAS가 내부 전달한 요청
```

현재 요청 종류는 다음과 같이 확인할 수 있다.

```java
request.getDispatcherType();
```

예외가 발생한 최초 요청에서는 `REQUEST`가 확인되고, WAS가 오류 처리 URL로 다시 전달한 요청에서는 `ERROR`가 확인된다.

```text
/error-ex
→ DispatcherType.REQUEST
→ 예외 발생

/error-page/500
→ DispatcherType.ERROR
→ 오류 화면 처리
```

---

## 9. 필터가 오류 처리 요청에도 동작할지 선택할 수 있다

오류 처리 요청도 필터 체인을 다시 지날 수 있지만, 모든 필터를 다시 실행해야 하는 것은 아니다.

예를 들어 요청 로그를 남기는 필터라면 일반 요청과 오류 요청을 모두 확인할 수 있다. 반면 이미 인증 검사를 마친 요청이라면 오류 화면을 보여주기 위해 인증 필터를 다시 실행할 필요가 없을 수 있다.

필터를 등록할 때 적용할 `DispatcherType`을 지정할 수 있다.

```java
registration.setDispatcherTypes(
        DispatcherType.REQUEST,
        DispatcherType.ERROR
);
```

위와 같이 등록하면 필터가 다음 두 요청에 모두 실행된다.

```text
일반 요청
→ REQUEST 필터 실행

오류 화면 내부 요청
→ ERROR 필터 실행
```

`REQUEST`만 지정하면 브라우저에서 처음 들어온 요청에만 필터가 적용되고, 오류 화면을 위한 내부 요청에서는 해당 필터가 실행되지 않는다.

따라서 필터의 역할을 보고 오류 처리 과정에서도 다시 실행해야 하는지 결정하면 된다.

## 10. 예외가 발생했을 때 인터셉터 메서드의 호출 결과

인터셉터는 컨트롤러 실행 전후에 같은 방식으로 항상 호출되는 것이 아니다. 컨트롤러가 정상적으로 작업을 마쳤는지, 실행 도중 예외가 발생했는지에 따라 호출되는 메서드가 달라진다.

`preHandle()`은 컨트롤러를 실행하기 전에 호출되므로, 컨트롤러 내부에서 예외가 발생하더라도 이미 실행을 마친 상태다.

반면 `postHandle()`은 컨트롤러가 정상적으로 반환한 뒤 호출된다. 컨트롤러가 결과를 반환하지 못하고 예외로 종료되면 실행할 시점 자체가 만들어지지 않는다.

`afterCompletion()`은 요청 처리가 끝나는 시점에 호출된다. 정상 처리뿐 아니라 예외로 종료된 경우에도 실행되며, 전달받은 `ex` 값을 통해 처리 중 예외가 발생했는지 확인할 수 있다.

```java
if (ex != null) {
    log.error("afterCompletion error", ex);
}
```

따라서 예외 발생 상황에서는 다음 결과가 나타난다.

```text
preHandle()       → 호출됨
Controller        → 예외 발생
postHandle()      → 호출되지 않음
afterCompletion() → 호출됨
```

이 차이를 알아두면 요청 완료 로그나 공통 자원 정리 코드를 어느 메서드에 두어야 할지 판단하기 쉬워진다. 컨트롤러가 성공했을 때만 필요한 작업은 `postHandle()`에 둘 수 있지만, 성공 여부와 관계없이 마무리해야 하는 작업은 `afterCompletion()`이 더 적합하다.

## 11. 오류 화면 처리에는 인터셉터를 다시 적용하지 않을 수 있다

오류 화면을 만들기 위한 내부 요청도 스프링 MVC의 처리 대상이 될 수 있다. 이 경로까지 기존 인터셉터가 적용되면, 처음 요청에서 이미 남긴 로그나 수행한 검사가 오류 화면 처리 과정에서 한 번 더 실행될 수 있다.

필터는 등록 단계에서 요청 종류를 기준으로 적용 범위를 선택할 수 있었지만, 스프링 인터셉터는 보통 URL 패턴으로 적용 대상을 조절한다. 따라서 오류 처리 전용 경로를 인터셉터 대상에서 제외하는 방식으로 중복 실행을 막는다.

```java
.excludePathPatterns("/error", "/error-page/**")
```

여기서 중요한 점은 인터셉터가 오류를 인식하지 못해서 제외하는 것이 아니다. 인터셉터의 역할상 오류 화면을 만드는 요청까지 다시 검사할 필요가 없으므로, 경로 설정을 통해 의도적으로 건너뛰게 만드는 것이다.

예를 들어 로그인 여부를 검사하는 인터셉터가 오류 경로에도 적용되면, 원래 오류를 보여줘야 하는 상황에서 로그인 페이지로 이동하거나 추가 오류가 발생할 수 있다. 오류 화면은 가능한 한 다른 공통 처리의 영향을 적게 받도록 구성하는 편이 안전하다.

## 12. Spring Boot에서는 오류 처리용 연결 작업을 직접 만들지 않아도 된다

앞에서는 오류 종류마다 이동할 경로를 등록하고, 그 경로를 받을 컨트롤러까지 직접 만들었다. 이 방식은 서블릿 컨테이너의 오류 처리 과정을 이해하는 데는 도움이 되지만, 애플리케이션마다 같은 기반 코드를 반복해서 작성해야 한다.

Spring Boot를 사용하면 이러한 기본 연결이 자동으로 준비된다. 애플리케이션 밖으로 전달된 예외나 `sendError()`로 기록된 오류는 공통 오류 경로인 `/error`에서 처리된다. 그리고 이 경로는 Spring Boot가 등록한 `BasicErrorController`가 담당한다.

개발자가 직접 작성했던 구성과 Spring Boot의 기본 구성을 비교하면 다음과 같다.

```text
직접 구성
오류 종류 등록 → 오류 처리 URL → 전용 컨트롤러 → 오류 화면

Spring Boot 기본 구성
오류 발생 → /error → BasicErrorController → 오류 화면 탐색
```

따라서 Spring Boot의 기본 기능을 사용할 때는 사용자 정의 `ErrorPage`와 오류 처리 컨트롤러를 반드시 만들 필요가 없다. 원하는 상태 코드에 맞는 화면 파일을 정해진 위치에 두는 것만으로 기본 오류 화면을 교체할 수 있다.

다만 `BasicErrorController`가 예외를 해결해 주는 것은 아니다. 이미 발생한 오류를 HTTP 응답과 오류 화면으로 정리하는 마지막 처리 지점에 가깝다.

## 13. 오류 화면은 더 구체적인 파일이 우선된다

Spring Boot는 오류 상태에 맞는 화면을 찾을 때 하나의 고정 파일만 확인하지 않는다. 상태 코드를 정확하게 지정한 화면과 상태 코드 범위를 묶은 화면을 함께 사용할 수 있다.

예를 들어 다음과 같이 파일을 둘 수 있다.

```text
templates/error/404.html
templates/error/4xx.html
templates/error/500.html
templates/error/5xx.html
```

404 오류가 발생하면 `404.html`이 `4xx.html`보다 먼저 선택된다. 정확히 일치하는 화면이 없을 때 범위 화면이 대신 사용된다.

```text
404 발생 → 404.html 우선 → 없으면 4xx.html
500 발생 → 500.html 우선 → 없으면 5xx.html
```

뷰 템플릿뿐 아니라 정적 HTML도 오류 화면으로 사용할 수 있지만, 같은 조건이라면 템플릿 방식이 먼저 선택된다. 템플릿은 서버가 전달한 오류 정보를 화면에 출력할 수 있고, 정적 파일은 미리 작성된 고정 내용만 보여준다는 차이가 있다.

이 우선순위를 사용하면 공통 화면과 개별 화면을 섞어서 구성할 수 있다. 대부분의 4xx 오류는 하나의 `4xx.html`로 처리하고, 사용자에게 별도 안내가 필요한 404만 `404.html`로 분리하는 식이다.

## 14. 오류 화면에 전달되는 값은 오류의 발생 방식에 따라 다르다

`BasicErrorController`는 오류 화면을 렌더링할 때 상태 코드, 요청 경로, 오류 이름 등 여러 값을 모델에 담을 수 있다. Thymeleaf에서는 필요한 값만 선택해서 출력한다.

```html
<li th:text="|status: ${status}|"></li>
<li th:text="|error: ${error}|"></li>
<li th:text="|path: ${path}|"></li>
```

모든 오류에서 모든 값이 채워지는 것은 아니다. `response.sendError(500)`은 500 상태를 전달하지만 자바 예외를 새로 발생시키지는 않는다. 이 경우 상태 코드와 오류 이름은 존재해도 예외 클래스나 스택 트레이스는 없을 수 있다.

반대로 컨트롤러에서 `RuntimeException`이 실제로 발생하면 예외와 관련된 정보가 만들어질 수 있다.

```text
sendError(500)
→ status, error, path 등 상태 코드 중심의 정보

RuntimeException 발생
→ 상태 코드 정보 + 예외 종류, 메시지, 추적 정보가 존재할 수 있음
```

즉, 설정에서 예외 정보를 포함하도록 허용했다고 해서 존재하지 않는 예외 정보까지 생성되는 것은 아니다. 설정은 현재 존재하는 정보 중 무엇을 모델에 포함할지 결정한다.

프로젝트 버전에 따라 설정 이름이 달라질 수 있으므로, 현재 사용하는 Spring Boot 버전의 설정 키를 기준으로 작성해야 한다. 현재 실습에서는 다음 계열의 옵션을 사용한다.

```properties
spring.web.error.include-message=always
spring.web.error.include-stacktrace=always
```

이 옵션들은 학습 과정에서 어떤 값이 전달되는지 확인할 때는 유용하지만, 운영 환경의 기본값으로 그대로 사용하기에는 주의가 필요하다.

## 15. 상세 오류 정보는 화면보다 서버 로그에 남기는 편이 안전하다

스택 트레이스, 예외 클래스, 내부 메시지는 개발자가 원인을 찾는 데 도움이 된다. 하지만 사용자 화면에 그대로 노출하면 서버 내부 구조, 클래스 이름, 사용 중인 라이브러리, 요청 데이터 일부가 드러날 수 있다.

따라서 개발 단계에서는 오류 모델을 화면에 출력해 흐름을 확인할 수 있지만, 실제 서비스에서는 사용자에게 필요한 안내만 보여주는 편이 적절하다.

```text
사용자 화면
→ 요청을 처리하지 못했다는 안내
→ 다시 시도하거나 문의할 방법

서버 로그
→ 실제 예외 종류
→ 스택 트레이스
→ 요청 식별값과 원인 분석 정보
```

오류 화면의 목적은 개발자에게 모든 원인을 보여주는 것이 아니라, 오류 상황에서도 사용자가 이해할 수 있는 응답을 제공하는 데 있다. 상세 원인은 화면과 분리해 로그에서 추적하는 구조가 더 안전하다.
